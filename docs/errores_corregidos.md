# Errores encontrados y correcciones aplicadas

Este registro describe los fallos reales que aparecieron durante la construcción del proyecto y cómo se resolvieron. Se conserva porque el enunciado exige supervisión de código generado con IA.

| # | Error | Causa | Corrección |
|---|-------|-------|------------|
| 1 | `pip : El término 'pip' no se reconoce...` | El `python` del PATH apuntaba a MSYS2 sin `pip`. | Se usó `py -m venv .venv` (Python 3.14) y se instalaron las dependencias dentro del entorno virtual. |
| 2 | `No module named pip` al ejecutar `python -m pip` | Mismo intérprete MSYS2 sin módulo pip. | Se abandonó ese intérprete; todos los comandos usan `.venv\Scripts\python.exe`. |
| 3 | `ModuleNotFoundError: requests` | `requests` no estaba en `requirements.txt`. | Se añadió `requests>=2.31.0` al archivo y se instaló en el venv. |
| 4 | `Faltan credenciales en el archivo .env` | No existía el archivo `.env`. | Se creó `.env.example` como plantilla y el usuario creó `.env` con sus valores reales. |
| 5 | `HTTP 401: Invalid API key or access token` al conectar con `ShopifyAPI` | Se estaba usando un valor `shpss_...` (Client Secret de la app) como si fuera un Admin API access token (`shpat_...`). | Se cambió el enfoque: el `shpss_...` se usa como `SHOPIFY_CLIENT_SECRET` y se solicita un token mediante `grant_type=client_credentials`. |
| 6 | API version `2024-01` obsoleta | Era la versión del script original; Shopify ya la retiró. | Se actualizó `main.py` a `2026-10`. El cliente nuevo usa `2026-01` por indicación del enunciado (ambas versiones estaban soportadas en la fecha del taller). |
| 7 | `Faltan variables en .env: SHOPIFY_CLIENT_ID` | El flujo de client credentials necesita también el ID de la app. | Se añadió `SHOPIFY_CLIENT_ID` al `.env` con el valor entregado por el usuario. |
| 8 | `400 - Oauth error app_not_installed` | La app del Dev Dashboard existía pero no estaba instalada en la tienda. | Se instaló la app desde Dev Dashboard → **Installs → Install app**, seleccionando la tienda `games4you-k5xbi4h0`. Tras esto la prueba devolvió `Conectado a: SecureHome Seguridad (...)`. |
| 9 | Endpoint escrito como `https://games4you-k5xbi4h0/admin/oauth/access_token` | `games4you-k5xbi4h0` solo es el subdominio; Shopify exige el dominio completo. | Se implementó `normalizar_shop()` para aceptar `games4you-k5xbi4h0`, `games4you-k5xbi4h0.myshopify.com` o la URL con `/admin`, y construir `https://<shop>.myshopify.com/admin/...`. |
| 10 | Traceback extenso con HTML en errores HTTP | `raise_for_status()` no mostraba el cuerpo; la página de error de OAuth ensuciaba la salida. | Se añadió `resumen_error()` en `shopify_client.py`, que extrae el `<title>` del HTML o el JSON del error. |
| 11 | Error de tipeo `diccionarioPython` y carácter extraño en docstrings | Errores de redacción al generar los módulos. | Se corrigieron los docstrings de `carrito/datos.py` y `carrito/orientado_objetos.py`. |
| 12 | El caso de prueba de envío pagado dejó de ejercitar esa ruta | Al cambiar el catálogo a tecnología, el carrito mínimo subió por encima de `$50.000` y el envío quedaba gratis. | Se incorporó el evento `accesorios_basicos` (productos económicos) y el caso `accesorios_basicos, 1 persona`, con total `$40.940` y envío `$3.990`. |
| 13 | `Access denied for products field. (ACCESS_DENIED)` al poblar el catálogo | La app instalada solo tenía los scopes `write_checkout_and_accounts_configurations` y `write_content`. | El usuario creó una nueva versión de la app en el Dev Dashboard con `read_products`, `write_products`, `write_inventory`, etc., la liberó y aprobó el cambio en la tienda. El token volvió a solicitarse y ya incluye los scopes necesarios. |
| 14 | El catálogo inicial no representaba una tienda tecnológica | Los primeros productos eran de fiesta y útiles escolares, pero el docente indicó que SecureHome Seguridad debía vender tecnología. | Se reemplazó `datos/catalogo.json` por 22 SKU tecnológicos (audio, periféricos, almacenamiento, pantallas, computadores, redes y accesorios), se renombró el evento `asado` a `trabajo_remoto`, se agregó `accesorios_basicos` y se actualizaron reglas, sustitutos, pruebas y documentación. Después se amplió a 34 SKU (incidencia 26). |
| 15 | `Access denied for name field. Required access: read_locations` al consultar `locations` | El token no incluye `read_locations` ni `read_markets_home`. | Se quitó el campo `name` de `LOCATIONS_QUERY`; solo se necesita el `id` para asignar el inventario. |
| 16 | `Field 'variants' is not defined by type 'ProductInput'` | Shopify 2026 cambió el modelo: las variantes ya no se crean dentro de `productCreate`. | Se creó el producto con `productCreate` y luego se agregó su variante con `productVariantsBulkCreate` (estrategia `DEFAULT`), usando `inventoryItem.sku`, `inventoryQuantities` y `optionValues`. |
| 17 | `collectionAddProducts is missing required arguments: id` / `doesn't accept argument 'collectionId'` | La API 2026 renombró los argumentos del mutation. | Se cambió la firma a `collectionAddProducts(id: $id, productIds: $productIds)`. Además se hizo `crear_colecciones()` idempotente: consulta las colecciones existentes y solo agrega los productos que faltan. |
| 18 | Aparecía un artículo ajeno al pasar al checkout | La tienda conservaba 17 productos de ejemplo de Shopify (snowboards y gift card) activos, visibles en el catálogo y en el flujo de compra. | Inicialmente se archivaron con `productUpdate(status: ARCHIVED)`; en la limpieza final se borraron definitivamente los 16 artículos ajenos (snowboards y cera) con `productDelete`, y se reactivó la Gift Card de crédito por pedido explícito. Quedan activos solo los 34 productos tecnológicos y la Gift Card. |
| 19 | Precios poco realistas para Chile | Los valores iniciales eran arbitrarios aunque la moneda de la tienda ya era CLP. | Se ajustaron los 34 precios a montos de mercado chileno (por ejemplo, notebook $599.990, monitor 24" $139.990, SSD 1 TB $74.990), manteniendo terminaciones habituales en CLP. `scripts/poblar_catalogo.py` ahora actualiza precios de productos existentes con `productVariantsBulkUpdate`. |
| 20 | Los productos no tenían imágenes | `productCreate` no incluía multimedia y el script original solo creaba variantes. | Se buscaron fotos reales con licencia comercial en Openverse/Flickr (sin marca de agua), se verificó que todas las URL respondieran `200 image/jpeg` y se guardaron en `datos/catalogo.json` como campo `imagen`. El script usa `productCreateMedia` para asociar la imagen, tanto en productos nuevos como existentes (ver incidencia 26). |
| 21 | `main.py` volvía a fallar con `SHOPIFY_ACCESS_TOKEN contiene el secreto de la app (shpss_...)` | El archivo seguía usando el primer enfoque (REST con `ShopifyAPI` y token `shpat_`), incompatible con las credenciales reales del proyecto. | Se reescribió `main.py` para delegar en `shopify_client.graphql_query()`, dejando `--info` como opción y marcando `--crear-ejemplo`/`--dry-run` como obsoletos. Ahora imprime `Conectado exitosamente a: SecureHome Seguridad (...)` y la API version `2026-01`. |
| 22 | El catálogo podía contener datos incompletos o SKUs duplicados sin que nada lo detectara | `cargar_catalogo()` hacía únicamente `json.load()`. | Se añadió `validar_catalogo()` en `carrito/datos.py`: comprueba claves obligatorias, tipos, SKUs únicos, precios y stock válidos, URLs de imagen HTTPS, sustitutos existentes y reglas coherentes. `cargar_catalogo()` lo invoca antes de devolver los datos. |
| 23 | Límites de tasa de Shopify podían interrumpir la carga del catálogo | El cliente no reintentaba ante HTTP 429 ni errores GraphQL `THROTTLED`. | Se agregó `peticion_con_reintento()` con backoff exponencial (`1, 2, 4, 8, 16 s`) y se detectan errores `THROTTLED` en `graphql_query()`. |
| 24 | No se registraban las respuestas fallidas de la API | El enunciado del agente pide registrar logs de errores; el cliente solo lanzaba excepciones. | Se añadió un `logger` en `shopify_client.py` que escribe `logs/shopify_errores.log` (carpeta ignorada por Git) con fecha, nivel y mensaje para errores de red, HTTP 429, fallos de token y errores GraphQL. |
| 25 | Faltaba la recomendación personalizada de productos similares con descuento por festividad | La primera versión del carrito solo resolvía stock, 2x1, cupón y envío; el usuario recordó este requisito adicional durante la revisión final. | Se agregó `carrito/recomendaciones.py` (función pura), la configuración `recomendaciones` en `datos/catalogo.json` y su integración en los tres paradigmas: imperativo (llamada al final del flujo), OOP (clase `Recomendador`) y funcional (función compuesta). El resultado incluye `recomendaciones` sin alterar el total; se añadieron 2 pruebas (7 en total). |
| 26 | `media` rechazado dentro de `productCreate` y catálogo mostrado completo en una sola página | Al ampliar el catálogo a 34 SKU, `productCreate` falló con `Field 'media' is not defined by type 'ProductInput'`; además las colecciones mostraban todos los productos juntos. | Se quitó `media` de `ProductInput` en `crear_producto()` y se llama a `productCreateMedia` después de crear la variante. Se añadió `scripts/actualizar_tema.py` (con `rest_request()` para assets) que fija 12 productos por página, conserva el control `pagination`, vincula `assets/techstore-paginas.css` y guarda respaldos en `backups/`. Previamente hicieron falta los scopes `read_themes`/`write_themes`. Se eliminaron 16 productos ajenos, se reactivó la Gift Card y se verificaron los 34 SKU activos con imagen y precio. |
| 27 | Faltaba la segmentación de clientes por tipo de usuario | El enunciado pedía precios y beneficios diferenciados, pero la primera versión del carrito solo atendía evento, personas y cupón. | Se añadió `carrito/segmentos.py` y la configuración `segmentos` en `datos/catalogo.json`. Los tres paradigmas aceptan el parámetro opcional `tipo_usuario` (`nuevo`, `frecuente`, `mayorista`; `None` = invitado). El descuento se aplica después del 2x1 y del cupón, con envío gratis para nuevo y mayorista y estilos de recomendación distintos. La API expone `GET /segmentos` y `POST /carrito` acepta `tipo_usuario`. Se agregaron 4 pruebas (11 en total). |
| 28 | Los 34 productos no aparecían en `/collections/all`; solo se veía la Gift Card | Los productos estaban `ACTIVE`, con precio, imagen y colección, pero tenían `publishedAt: null`. En Shopify, `ACTIVE` no equivale a publicado en el canal Online Store. | Se añadió `publishedAt` a `PRODUCTOS_QUERY` y la mutación `productUpdate(input: {id: $id, publishedAt: $fecha})` en `scripts/poblar_catalogo.py`. El script genera la fecha UTC con `fecha_publicacion()` y publica tanto productos nuevos como existentes que aún no estén publicados. Después de publicar, el catálogo se navega en páginas de 12 productos gracias al cambio del tema descrito en la incidencia 26. |
| 29 | Los tres paradigmas no producían la misma cantidad de bytes al crear los JSON | El bloque final de `imperativo.py` conservaba claves de depuración ausentes en POO y funcional: `resumen` tenía 15 claves en vez de 4, las líneas del carrito usaban `precio_original` en lugar de `precio_unitario_original` y `regalo` incluía `motivo`. Ese desajuste de esquema aportaba 485 bytes. | Se añadió al final de `imperativo.py` un bloque puramente imperativo que reconstruye cada línea campo por campo, elimina `precio_original`, inserta `precio_unitario_original` justo después de `precio_unitario`, quita `motivo` de `regalo` y deja `resumen` solo con `cantidad_items`, `subtotal`, `descuento_total` y `total_final`. |
| 30 | Aun con el esquema igualado, los bytes seguían sin coincidir | El `open(..., "w")` del imperativo no fijaba `newline`, así que Windows convirtió sus 141 saltos `\n` en `\r\n` (141 bytes extra), mientras POO y funcional escribían LF. Resultado: 3408 bytes contra 2782. | Los tres motores escriben con `RUTA_RESULTADO.open("w", encoding="utf-8", newline="\n")` y añaden un `\n` final. Corregidos el esquema y los saltos, los tres JSON quedaron en 2782 bytes y con el mismo SHA-256; con el catálogo actual son 2472 bytes y `0B99768E…26093`. |

## Incidencias retiradas y reutilización de números

Los números **#29** y **#30** se habían reservado en `CONTINUAR.md` para el catálogo anterior de 34 SKU (fotos con fondo blanco y ajuste de `presentmentPrices`). Esas dos incidencias **se retiraron** porque el catálogo fue sustituido por 11 productos reales de Shopify y 3 SKU de prueba del kit. Los números quedaron libres y se reutilizan arriba para los dos fallos reales detectados al crear los tres paradigmas: desajuste de esquema (#29) y saltos CRLF (#30). El registro queda en 30 incidencias reales.
